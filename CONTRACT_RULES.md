---------------------------------------------------------------------

1. Назначение документа
----------------------
Данный документ фиксирует контракт правил, используемых системой.

Цели контракта:
- обеспечить воспроизводимость поведения системы;
- исключить «тихие» изменения логики;
- чётко разделить ответственность между:
  - оператором (что можно менять);
  - системой (как это применяется).

Источники истины:
- rules.xlsx — единственный источник бизнес-решений;
- YAML — архитектура расчётов, формат отчётов, редко меняющиеся параметры;
- код — исполнитель контракта, но не его источник.

---------------------------------------------------------------------

2. Общая модель правил
---------------------

2.1 Активность
- Любое правило имеет поле `enabled`.
- `enabled = 1` — правило активно.
- `enabled = 0` — правило игнорируется.

2.2 Уникальность
Для каждого типа правил определён ключ уникальности.
Для каждого ключа допускается ровно одно активное правило.

Нарушение уникальности → ошибка конфигурации → расчёты не запускаются.

3. Структура rules.xlsx
----------------------

3.1 Лист `meta`
Используется для версионирования и совместимости.

Текущая фактическая схема (как в rules.xlsx сейчас):

| key          | value | required |
|--------------|-------|----------|
| ruleset_name | string| no       |
| version      | int   | yes      |
| updated_at   | datetime | yes   |
| updated_by   | string| no       |
| comment      | string| no       |

Правила:
- `version` — версия контракта rules (Contract version).
- При чтении допускается алиас: `contract_version` (если появится позже).

Несовпадение version/contract_version с ожидаемой версией кода → отказ запуска job.

---------------------------------------------------------------------

3.2 Лист `exclude_time`
Назначение: исключить временные интервалы из расчётов.

Фактическая схема (как в rules.xlsx сейчас):

| column     | type        | required |
|------------|-------------|----------|
| id         | string      | yes |
| enabled    | int (0/1)   | yes |
| analyzers  | string (CSV)| yes |
| partner    | string      | no  |
| start_dt   | datetime    | yes |
| end_dt     | datetime    | yes |
| reason     | string      | yes |
| created_by | string      | no  |
| created_at | datetime    | no  |

Правила:
- `analyzers` — CSV список ключей анализаторов (lowercase); пример: `wallet,conversion`.
- правило применяется, если analyzer входит в список.
- start_dt < end_dt — обязательно.

Примечание (расширение схемы):
- Если позже будут добавлены `card`/`pool`, они считаются опциональными фильтрами и не ломают v2.

---------------------------------------------------------------------

3.3 Лист `thresholds_partner`
Назначение: пороги метрик анализаторов.

Фактическая схема (как в rules.xlsx сейчас):

| column        | type      | required |
|---------------|-----------|----------|
| id            | string    | yes |
| enabled       | int (0/1) | yes |
| analyzer      | string    | yes |
| partner       | string    | yes |
| metric        | string    | yes |
| threshold     | number    | no  |
| threshold_min | number    | no  |
| threshold_max | number    | no  |
| min_events    | number    | no  |
| reason        | string    | yes |
| updated_by    | string    | no  |
| updated_at    | datetime  | no  |

Ключ уникальности:
(analyzer, partner, metric)

Контракт порогов (v2):
- канонический механизм: ровно одно из `threshold_min` или `threshold_max` должно быть заполнено (XOR).
- `threshold` считается DEPRECATED (для миграции) и должен быть пустым после переезда.
- Если заполнены `threshold_min/threshold_max` — поле `threshold` игнорируется.
- Если заполнен только `threshold` (миграционный режим) — код может трактовать его согласно metric
  (conversion_rate → threshold_min, api_cancel_rate/error_streak → threshold_max) и обязан логировать WARNING.

Допустимые metric (v2):
- `conversion_rate` — доля успешных операций (%), сравнение: >= threshold_min
- `api_cancel_rate` — доля отмен по API (%), сравнение: <= threshold_max
- `error_streak` — подряд ошибок до первого успеха (целое), сравнение: <= threshold_max

Ограничения значений:
- rate-метрики: 0..100
- error_streak: int >= 0

3.4 Лист `wallet_limits`
Назначение: лимиты сумм для wallet-анализатора.

Фактическая схема (как в rules.xlsx сейчас):

| column      | type                         | required |
|-------------|------------------------------|----------|
| id          | string                       | yes |
| enabled     | int (0/1)                    | yes |
| scope       | string (partner / group)     | yes |
| scope_value | string                       | yes |
| limit_type  | string                       | yes |
| limit_value | number                       | yes |
| reason      | string                       | yes |
| updated_by  | string                       | no  |
| updated_at  | datetime                     | no  |

Допустимые значения:
- limit_type: daily_max_amount
- scope: partner, group

Ключ уникальности:
(scope, scope_value, limit_type)

3.5 Лист `access`
Назначение: таблица доступа для Telegram-бота (Control Plane).

| column   | type      | required |
|----------|-----------|----------|
| chat_id  | string/int| yes |
| user_id  | string/int| no  |
| level    | string/int| yes |
| note     | string    | no  |
| enabled  | int (0/1) | yes |

Правила:
- access управляет правами выполнения команд бота/оператора.
- Интерпретация level и user_id определяется контрактом бота (см. CONTRACT_BOT.md).

| note           | string    | no  |

4. Приоритеты и fallback
-----------------------

4.1 Thresholds
1) (analyzer, partner, metric)
2) (analyzer, default, metric)
3) отсутствие правила → fallback логики анализатора

4.2 Wallet limits
1) scope=partner
2) scope=group
3) отсутствие лимита → лимит не применяется

---------------------------------------------------------------------

5. Обязательные валидации
------------------------
Перед применением rules система обязана проверить:
- наличие обязательных колонок;
- корректность типов данных;
- уникальность активных правил;
- допустимые значения metric / scope / limit_type;
- XOR-правило threshold_min/threshold_max (канон v2);
- отсутствие конфликтных копий rules.xlsx (Dropbox conflicted copy) — при наличии отказ запуска.

При любой ошибке:
- rules не применяются;
- job не запускается;
- фиксируется событие `config_validation_failed` (Observability).

---------------------------------------------------------------------

6. Версионирование и воспроизводимость
------------------------------------
- rules_version — хэш содержимого rules.xlsx;
- version/contract_version — версия контракта.

Каждый job сохраняет snapshot:
- rules_version;
- version/contract_version.

Несовпадение версии контракта → отказ запуска.

---------------------------------------------------------------------

7. Изменение правил
------------------
- Прямое редактирование Excel не рекомендуется.
- Операционные изменения выполняются через Telegram-бот.

Бот обязан:
- управлять enabled;
- предотвращать конфликты;
- писать audit-events.

8. Гарантии
-----------
При соблюдении контракта система гарантирует:
- отсутствие неявных приоритетов;
- отсутствие «тихих» перекрытий;
- объяснимость любого результата расчёта.
