Управляемая аналитическая платформа (Contract v1)
Статус документа

Версия: v1.0
Назначение: архитектурный контракт (Contract of Reproducibility)
Обязателен к соблюдению при любых изменениях системы
Код не считается корректным, если нарушает данный контракт

1. Цель системы 

Система предназначена для:
автоматизированной загрузки данных
аналитических расчётов
формирования отчётов и алертов
управляемого изменения поведения без деплоя
полной воспроизводимости решений и запусков

Ключевое требование:

Любой результат системы должен быть объясним постфактум.

2. Базовые принципы
2.1 Разделение ответственности

Система разделена на три независимых контура:
Control Plane — Контур управления
Отвечает на вопрос: почему система ведёт себя так.
- бизнес-правила
- пороги
- исключения
- роли и политики доступа
- параметры расписаний

Хранение: Dropbox
Формат: Excel (rules) + YAML (roles, policies)
Execution Plane — Контур исполнения
Отвечает на вопрос: что система делает.
- downloader’ы
- анализаторы
- scheduler

отчёты

мониторинги

Ключевое правило:
Execution Plane не содержит бизнес-решений и не интерпретирует правила.

Observability Plane — Контур наблюдаемости

Отвечает на вопрос: что реально происходило.

события

ошибки

ручные вмешательства

итоги запусков

Назначение: аудит, воспроизводимость, доверие к системе.

3. Управление конфигурациями (Control Plane)
3.1 Артефакты конфигурации

Все конфигурации являются версионируемыми артефактами.

Тип	Назначение	Формат	Расположение
Rules	Бизнес-правила	Excel	/config/rules/
Roles	Роли пользователей	YAML	/config/access/roles.yaml
Policies	Политики команд	YAML	/config/access/policies.yaml
3.2 Версии конфигураций

Каждый конфиг имеет:

version или hash

loaded_at

источник (Dropbox)

Версии:

rules_version

roles_version

policy_version

Версии обязательно фиксируются в событиях и job’ах.

3.3 Reload конфигураций

Конфигурации перезагружаются:

перед каждой Telegram-командой

перед каждым запуском job

Используется:

TTL-кэш (60–120 секунд)

ручная команда /reload access

fail-safe поведение

Поведение при ошибке загрузки:

Telegram: fail-closed (команды запрещены)

Job’ы: fail-safe (используется последний валидный snapshot)

4. Роли и политики доступа
4.1 Роли (roles.yaml)

Роль отвечает на вопрос: кто ты.

Минимальные роли:

Observer

Operator

Maintainer

Owner

4.2 Политики (policies.yaml)

Политика отвечает на вопрос: что тебе можно.

Политики управляют:

разрешёнными командами

доступом к job’ам

возможностью reload’ов

опасными действиями

5. Job-модель (Execution Contract)
5.1 Что такое Job

Job — атомарное намерение выполнить разрешённое действие.

Примеры:

run_wallet_cycle

run_downloader

run_hourly

reload_access

5.2 Политика конкурентности

Один job одного типа может выполняться одновременно

Параллельные одинаковые job’ы запрещены

При конфликте:

новый job отклоняется (job_rejected)

возвращается running_job_id

5.3 Snapshot-правило

Перед стартом job:

загружаются конфиги

формируется snapshot версий

job выполняется строго по snapshot

Конфиги не меняются в процессе выполнения job.

6. Event Model (Observability Contract)
6.1 Событие

Event — неизменяемый факт, записываемый append-only.

Обязательные поля:

event_id

timestamp

type

severity

job_id (nullable)

actor (nullable)

versions {rules, roles, policy}

payload

6.2 Типы событий (v1)
Конфигурации

config_reload_started

config_reload_finished

config_reload_failed

Telegram / Intent

intent_received

intent_accepted

intent_rejected

Job

job_requested

job_rejected

job_started

job_finished

job_failed

Артефакты

artifact_registered

artifact_uploaded

Уведомления

alert_sent

7. Audit Trail и ретеншн
7.1 Audit Trail v1 (обязательно логируется)

изменения конфигов

все Telegram-команды

все job’ы (request → start → finish/fail)

входные и выходные файлы (hash)

отправленные уведомления

7.2 Хранение

Hot storage: БД событий, 30 дней

Cold storage: Dropbox архив по дням (events_YYYY-MM-DD.jsonl)

Архив хранится бессрочно

8. Воспроизводимость (Contract of Reproducibility)

Система считается корректной, если можно восстановить:

кто инициировал действие

по каким правилам оно выполнялось

какие версии конфигов применялись

какие входные данные использовались

чем действие завершилось

Логируются решения и переходы, а не вычисления.

9. Антипаттерны (запрещено)

❌ хранить бизнес-правила в коде

❌ запускать job’ы напрямую из Telegram без job-модели

❌ принимать команды по устаревшим ролям/политикам

❌ изменять конфиги без события

❌ терять связь job ↔ правила ↔ актор

10. Изменения контракта

Любые изменения данного документа:

оформляются как новая версия

обсуждаются отдельно

не допускаются “тихо”

Итоговая формула

Система управляется данными,
исполняется кодом,
наблюдается через события,
и сохраняет доверие через воспроизводимость.
