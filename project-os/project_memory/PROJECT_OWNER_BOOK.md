# Что это за система

## Назначение проекта

**analizis** — это автоматический помощник, который работает **круглосуточно на облачном сервере** (платформа Railway). Он:

- забирает данные с внешних сайтов (Antares, Raccoon, Bakai);
- считает отчёты по правилам из Excel-файла **rules.xlsx**;
- присылает результаты в **Telegram**;
- по запросу операторов **меняет настройки карт** в Antares через сценарий **WalletEditor**.

Один и тот же бот в Telegram — это «пульт управления» и «окно результатов».

## Какие бизнес-задачи решает

| Задача | Как система помогает |
|--------|----------------------|
| Контроль конверсии и проблемных карт | Процесс **Conversion** строит отчёт, находит проблемные карты, может передать их в WalletEditor |
| Операционная работа с картами | **WalletEditor** выполняет действия по списку из Excel (снять партнёра, сменить статус и т.д.) |
| Мониторинг Raccoon | Отчёты по PayIn: каждые ~10 минут, ежедневная сводка по конверсии, отдельный «кошелёчный» отчёт |
| Курс RUB на Bakai | Автоматическая проверка курса и уведомление при изменении |
| Почасовая и кошелёчная аналитика Antares | Отчёты **hourly** и **wallet** по расписанию |
| Выгрузка и разбор файлов Antares | Процесс **download**: скачивание → Dropbox → анализ conversion/payout |
| Единые правила для всех | **rules.xlsx** — кто имеет доступ к боту, расписание, пороги, партнёры |

## Кто использует

| Роль | Что делает |
|------|------------|
| **Операторы** | Отправляют Excel в WalletEditor, смотрят отчёты в чатах, иногда запускают команды бота |
| **Аналитики / контроль** | Читают отчёты Conversion, Raccoon, hourly, wallet |
| **Администратор rules** | Редактируют rules.xlsx в Dropbox, перезагружают правила командой `/reload_rules` |
| **Технический администратор** | Настраивает переменные окружения на Railway, следит за логами (это уже ближе к PROJECT_BOOK) |

# Основные возможности

## WalletEditor

**Зачем нужен.** Чтобы не вручную открывать каждую карту в Antares: оператор присылает таблицу Excel, система по строкам выполняет действия (например, убрать партнёра с карты).

**Кто использует.** Операторы в разрешённых Telegram-чатах; у каждого свой профиль и своя очередь задач.

**Какой результат.** В тот же чат приходит краткая сводка и файл Excel с колонками: что получилось (OK / SKIP / FAIL), комментарий, дата обработки. Дополнительно (если настроено) история копится в общий файл на Dropbox.

---

## Conversion

**Зачем нужен.** Анализ файлов конверсии с Antares: какие карты проблемные, отчёт в Telegram и Excel.

**Кто использует.** Косвенно — все, кто читает чат «аналитики» (analiz); запускается автоматически после выгрузки **download** или при обработке файла из Dropbox.

**Какой результат.** Сообщения и отчёт в Telegram; при настройке — автоматическая постановка проблемных карт в очередь WalletEditor (отдельный чат для conversion→WE).

---

## Raccoon

**Зачем нужен.** Мониторинг PayIn на портале Raccoon (raccoon.it.com): частые сводки, предупреждения о просадке конверсии, дневной отчёт, отдельный отчёт в стиле «кошелька».

**Кто использует.** Сотрудники, подписанные на чаты Raccoon (см. раздел Telegram).

**Какой результат.** Текстовые отчёты в Telegram; данные берутся из скачанного Excel PayIn.

---

## Bakai

**Зачем нужен.** Следить за курсом покупки RUB на сайте bakai.kg и сообщать, когда курс изменился.

**Кто использует.** Те, кто в чатах «текущий курс» и «алерт при изменении».

**Какой результат.** Сообщения в Telegram; ночью и рано утром (вне окна 08:00–23:55 по Москве) проверка **не выполняется**.

---

## Rules (rules.xlsx)

**Зачем нужен.** Один файл, где записано: кто может нажимать команды бота, как часто запускать процессы, пороги для партнёров, списки для hourly, маршруты чатов (опционально).

**Кто использует.** Администратор правил; система читает файл автоматически.

**Какой результат.** Без корректного rules.xlsx сервис **не запустится** или откажет в доступе / расписании.

---

## Telegram

**Зачем нужен.** Единый интерфейс: команды, статус, приём файлов WalletEditor, доставка всех отчётов.

**Кто использует.** Все роли выше.

**Какой результат.** Сообщения, файлы, ответы на команды — в настроенных чатах (идентификаторы чатов задаёт администратор на сервере, не в rules).

---

## Dropbox

**Зачем нужен.** Хранилище: rules.xlsx, входящие файлы для анализа, обработанные файлы, общая «память» системы (state), журнал WalletEditor.

**Кто использует.** Система постоянно; люди — когда кладут файлы или правят rules.

**Какой результат.** Синхронизация правил и состояния; файлы conversion/payout попадают в папки «вход» и «обработано».

# Карта системы

## Общая схема

```
Человек (оператор / аналитик)
        ↓
   Telegram (бот)
        ↓
   Система на сервере (всегда включена)
        ↓
   ┌──────────────────────────────────────┐
   │  Отчёты в чаты  │  Действия в Antares │
   │  (текст, Excel) │  (WalletEditor)     │
   └──────────────────────────────────────┘
        ↑
   Dropbox (rules, файлы, история WE)
        ↑
   Внешние сайты: Antares, Raccoon, Bakai
```

## Где что живёт внутри системы

```
                    ┌─────────────┐
                    │  rules.xlsx │
                    │  (Dropbox)  │
                    └──────┬──────┘
                           │ расписание, доступ, пороги
     ┌─────────────────────┼─────────────────────┐
     ▼                     ▼                     ▼
 WalletEditor          Conversion            Raccoon / Bakai
 (файл от человека)    (файлы Antares)       (сайты + rules)
     │                     │                     │
     ▼                     ▼                     ▼
 Antares UI            Отчёты + TG            Отчёты + TG
```

**Планировщик (Scheduler)** — внутренняя «будильник»: каждые несколько секунд смотрит rules и запускает процессы по расписанию. Человеку не нужно нажимать кнопку, если процесс включён в листе **schedules**.

Ниже — пошагово: что видит человек и что делает система.

## WalletEditor

### Кто начинает

Оператор в **разрешённом** Telegram-чате отправляет боту файл **.xlsx** (не команда, а именно документ).

### Полный путь

```
Пользователь отправляет файл .xlsx
        ↓
Бот получает сообщение (сервер постоянно «слушает» Telegram)
        ↓
Проверка: этот чат в списке разрешённых?
        ↓
Проверка: это файл .xlsx?
        ↓
Проверка: известен ли Telegram user_id оператора?
        ↓
Проверка: настроены ли логин/пароль Antares для его профиля?
        ↓
Бот отвечает: «Файл получен»
        ↓
Скачивание файла на сервер (временная папка)
        ↓
Постановка задачи в очередь профиля оператора
        ↓
Бот отвечает: «Добавлено в очередь, размер очереди: N»
        ↓
(Когда подошла очередь) Запуск обработки одним «работником» на профиль
        ↓
Вход в Antares (браузер без окна на сервере; сессия может сохраняться)
        ↓
Чтение Excel: для каждой строки — карта + действие + значение
        ↓
Для каждой карты: открыть карту → выполнить действия → сохранить
        ↓
Формирование результата Excel
        ↓
Отправка в Telegram: текст-сводка + файл результата
        ↓
(Фоном, если настроено) Дописать строки в общий журнал на Dropbox
        ↓
Через ~30 сек удаление временных файлов на сервере
```

### Таблица шагов

| Шаг | Что происходит | Что проверяется | Что может пойти не так |
|-----|----------------|-----------------|------------------------|
| 1. Отправка файла | Документ уходит в бот | — | Не тот чат → «Чат не разрешён» |
| 2. Тип файла | Только `.xlsx` | Расширение имени | PDF/CSV → отказ |
| 3. Оператор | Сопоставление user_id → профиль (DENIS, IVAN и т.д.) | Список в настройках сервера | «Не настроен профиль» |
| 4. Учётные данные | Логин/пароль Antares для профиля | Оба поля заполнены | «Профиль настроен неполностью» |
| 5. Очередь | Задачи одного профиля — **по одной**; разные профили — параллельно | — | Долгое ожидание при большой очереди |
| 6. Вход в Antares | Автоматический логин | Сайт доступен | Таймаут, неверный пароль |
| 7. Строки Excel | Колонки **card**, **action**, **value** обязательны | Нет пустых обязательных колонок | «Отсутствуют колонки» |
| 8. Действия | См. список действий ниже | Карта есть в Antares | FAIL в строке + комментарий |
| 9. Результат в TG | Сводка + файл | Telegram доставляет | Бот «молчит» при сбое отправки (см. Ошибки) |
| 10. Журнал Dropbox | Не блокирует Telegram | Dropbox доступен | Журнал может отстать; в TG результат уже есть |

### Допустимые действия в Excel (колонка `action`)

| action | Что делает (простыми словами) | value |
|--------|------------------------------|-------|
| `remove_partner` | Убрать партнёра с карты | Имя партнёра |
| `add_partner` | Добавить партнёра | Имя партнёра |
| `set_status` | Поставить статус карты | Текст статуса (из разрешённого списка в системе) |
| `set_direction` | Направление | Например «Вход» |
| `add_group` / `set_group` | Группы на карте | Название группы |
| `clear_groups` | Очистить группы | Может быть пустым |

Регистр в `action` не важен — система приводит к нижнему регистру.

### Что получает пользователь

1. Сразу: «Файл получен», затем «Добавлено в очередь…»  
2. После обработки: текст со статистикой (сколько OK / FAIL / SKIP).  
3. Файл **wallet_editor_result_…xlsx** с колонками в том числе: `Дата отключения`, `card`, `action`, `value`, `status`, `comment`.

## Conversion

### Кто начинает

- **Автоматически** после процесса «выгрузка download» (Antares → Dropbox → анализ).  
- **Автоматически** при появлении файла conversion в Dropbox (если запущен разбор).  
- **Не** запускается вручную отдельной командой бота (есть `/run_download`, который включает conversion внутри себя).

### Полный путь

```
Появляются файлы conversion_*.xlsx и card_*.xlsx (из выгрузки или в Dropbox)
        ↓
Система скачивает их с Dropbox во временную папку
        ↓
(Опционально) Считает «отпечаток» файлов — запоминает, менялись ли данные
        ↓
Важно: даже если данные те же — анализ всё равно выполняется (пропуск по отпечатку НЕ включён)
        ↓
Чтение правил конверсии из rules.xlsx
        ↓
Расчёт: проблемные карты, метрики, отчёт
        ↓
Отправка отчёта в Telegram (чат analiz)
        ↓
Сохранение Excel-отчёта
        ↓
Перемещение исходных файлов в папку «обработано» на Dropbox
        ↓
(Если настроено) Сообщение в чат Conversion→WalletEditor + постановка карт в очередь WE
```

### Проверки и сбои

| Этап | Проверки | Сбои |
|------|----------|------|
| Файлы | Имена вида conversion_*, card_* | Нет файла → ошибка в чат analiz |
| Колонки в conversion | «Карта», «Статус», «Дата/Время создания» | Неверная структура → сбой анализа |
| Dropbox | Доступ, пути вход/обработано | Не переместит файл — сообщение об ошибке |
| Память «отпечатка» | Сравнение с прошлым запуском | Только для статистики; отчёт не отменяет |
| Hook в WalletEditor | Карта и партнёр не пустые | Нет env → шаг просто пропускается, conversion не падает |

### Что получает пользователь

- Сообщения о ходе в чате **analiz** (старт, успех/ошибка выгрузки).  
- Итоговый отчёт conversion (текст + при необходимости файл).  
- При включённом мосте: информационное сообщение в чат **conversion WalletEditor** и позже — результаты WE по проблемным картам.

## Raccoon Hourly

### Кто начинает

- **По расписанию** из rules (строка с типом задачи `raccoon_hourly`) — точное расписание в prod: **неизвестно**.  
- **Вручную:** команда `/run_hourly_raccoon` (нужен доступ в rules).

### Полный путь

```
Старт задачи
        ↓
Вход на Raccoon (логин/пароль с сервера)
        ↓
Скачивание PayIn в Excel → временная папка hourly_raccoon
        ↓
Построение отчёта «по методам» за окно из rules
        ↓
Сравнение с прошлым отчётом (чтобы не слать дубликат без изменений) — логика отчёта
        ↓
Отправка основного отчёта в чат «Hourly Raccoon»
        ↓
Проверка просадки конверсии по порогам из rules
        ↓
При необходимости — алерт в чат «Raccoon Wallet»
```

### Проверки и сбои

| Этап | Что проверяется | Сбои |
|------|-----------------|------|
| Учётные данные Raccoon | Логин/пароль на сервере | Задача падает, сообщение об ошибке |
| Чаты Telegram | Два разных chat_id настроены | «Не задан TELEGRAM_CHAT_ID_…» |
| Excel PayIn | Колонки по правилам Raccoon | Пустой/битый файл → сбой отчёта |
| Пороги | Из rules (thresholds_partner и др.) | Неверные rules → неверные алерты |

### Что получает пользователь

- Регулярный текстовый отчёт PayIn (чат **Hourly Raccoon**).  
- Отдельные предупреждения о конверсии (чат **Raccoon Wallet**).

## Raccoon Daily

### Кто начинает

- **Только по расписанию** (`raccoon_daily_conversion`) — отдельной команды в боте **нет**.  
- Расписание в prod: **неизвестно**.

### Полный путь

```
Старт задачи (планировщик)
        ↓
Чтение того же файла PayIn, что собирает Raccoon Hourly
        (/tmp/hourly_raccoon/payin.xlsx — если hourly ещё не скачал, файл может отсутствовать)
        ↓
Отбор операций за вчерашние сутки (Москва)
        ↓
Расчёт конверсии по партнёрам/методам
        ↓
Отправка сводки в чат Raccoon Wallet
```

### Зависимость от Hourly

Дневной отчёт **не скачивает** сайт сам — он читает уже скачанный PayIn. Если hourly не работал, daily может не найти данные (**неизвестно**, есть ли отдельная защита в тексте ошибки — при сбое смотрите логи).

### Что получает пользователь

Один текстовый отчёт за предыдущий календарный день в чат **Raccoon Wallet**.

## Raccoon Wallet (отдельный процесс)

Кратко: по расписанию или `/run_raccoon` — скачивание PayIn с Raccoon за период из rules, анализ «как wallet-отчёт», отправка в **Raccoon Wallet**. Настройки только из rules.xlsx (не из старого YAML).

## Bakai

### Кто начинает

- Расписание `rate` в rules.  
- Команда `/run_rate`.

### Полный путь

```
Старт
        ↓
Проверка времени: сейчас между 08:00 и 23:55 по Москве?
        ↓  нет → тихий выход (ничего не шлёт)
        ↓  да
Открытие bakai.kg в браузере на сервере
        ↓
Чтение курса покупки RUB
        ↓
Сравнение с сохранённым прошлым значением (файл на сервере, временный)
        ↓
┌─ первый раз → сообщение «текущий курс» в чат «текущий»
├─ курс изменился → алерт в чат «изменение»
└─ без изменений → сообщение «без изменений» в чат «текущий»
        ↓
При ошибке: до 3 попыток, затем сообщение об ошибке (+ возможно скриншот)
```

### Что получает пользователь

- Обычные сообщения о курсе.  
- Яркий алерт при изменении.  
- Ночью (вне окна) — **тишина** (это норма, не поломка).

## Rules — что происходит после изменения rules.xlsx

### Цепочка

```
Администратор сохраняет rules.xlsx в Dropbox
        ↓
В течение ~30 секунд (или сразу при /reload_rules) система подтягивает файл
        ↓
Проверка структуры: обязательны листы meta, exclude_time, access, commands
        ↓
Если файл битый при СТАРТЕ сервиса — сервис не поднимется
        ↓
Если битый при работе — зависит от ситуации; политика «оставить старые правила» при ошибке sync: неизвестно (E6)
        ↓
Правила превращаются во внутренний «снимок» (snapshot) для быстрого чтения
        ↓
Применяются: доступ к командам, расписание, пороги, параметры hourly, Raccoon, WE registry timeouts
        ↓
Команда /reload_rules — принудительное обновление + сброс таймеров планировщика
```

### Что вступает в силу автоматически

| Изменение в rules | Когда действует |
|-------------------|-----------------|
| schedules (включить/выключить задачу) | После sync / reload, планировщик подхватит за ~5–10 сек |
| access / commands | Следующая команда пользователя |
| job_params (интервал hourly и т.д.) | Следующий запуск hourly |
| Пороги партнёров | Следующий соответствующий отчёт |
| telegram_routes (если лист есть) | Зависит от флага на сервере «брать чаты из rules» — **неизвестно**, включён ли в prod |

### Что ломает систему (критично)

- Удалены обязательные листы или колонки.  
- Неверный формат расписания (пустой cron, нулевой интервал).  
- Сломанный Excel (не открывается как zip/xlsx).  
- **Неизвестно:** полный список ошибок на уровне каждой строки — для проверки есть `/rules_validate` в боте (нужен доступ).

# Telegram

Идентификаторы чатов (числа вида `-100…`) задаются **администратором на сервере Railway**, не в rules. Ниже — **назначение** чатов по именам настроек (без реальных номеров).

## Чаты и назначение

| Название настройки (логическое) | Назначение | Какие сообщения | Кто смотрит | Процессы |
|--------------------------------|------------|-----------------|-------------|----------|
| **Чат analiz** | Главный операционный канал Antares | Старт/ошибки download, conversion, payout, итоги выгрузки | Аналитики, дежурные | download, conversion, payout |
| **Чат hourly (platform)** | Почасовой отчёт Antares | Текст hourly-сводки | Аналитика | hourly |
| **Чат wallet (platform)** | Кошелёчный отчёт Antares | Текст wallet-отчёта | Аналитика | wallet |
| **Чат Hourly Raccoon** | Частый PayIn Raccoon | Отчёт ~10 мин | Команда Raccoon | raccoon_hourly |
| **Чат Raccoon Wallet** | Raccoon: алерты, wallet-отчёт, daily conversion, ошибки скачивания | Алерты конверсии, daily, wallet Raccoon | Команда Raccoon | raccoon_hourly (алерты), raccoon_wallet, raccoon_daily |
| **Чат Conversion → WalletEditor** | Служебный: сколько карт ушло в WE | Инфо после conversion, ошибки моста, результаты WE по авто-профилю | Операторы WE / дежурные | conversion hook + WE |
| **Чат Bakai «текущий»** | Курс без изменений, ошибки, первый замер | Текст курса, скрин при ошибке | Финансы / дежурные | rate |
| **Чат Bakai «алерт»** | Изменение курса | Сообщение с дельтой | Финансы | rate |
| **Разрешённые чаты WE** | Только **приём** Excel | Ответы бота на файл, результаты WE | Операторы | WalletEditor ingest |
| **Чат emergency** | Зарезервирован | Сейчас не подменяет другие чаты | Админ | — |

### Команды бота (для людей с доступом в rules)

| Команда | Действие |
|---------|----------|
| `/start`, `/help` | Справка |
| `/status` | Что сейчас выполняется (расширенно — если включён режим наблюдения на сервере) |
| `/whoami` | Ваш user_id и уровень доступа |
| `/reload_rules` | Обновить rules из Dropbox |
| `/run_wallet`, `/run_hourly`, `/run_download`, `/run_rate` | Запустить процесс вручную |
| `/run_raccoon`, `/run_hourly_raccoon` | Raccoon wallet / hourly |
| `/rules_validate` | Проверить rules и прислать отчёт в чат |

**Нет команды** для Raccoon Daily — только расписание.

# rules.xlsx — простым языком

## Что это

**Единая книга правил** в Excel на Dropbox. Без неё бот не знает: кого пускать, когда запускать задачи, какие пороги у партнёров, как собирать hourly.

## Кто может менять

Люди с доступом к папке Dropbox и дисциплиной версий. После правки желательно `/reload_rules` или подождать автосинхронизацию.

## Что контролирует (основные листы)

| Лист | Простыми словами |
|------|------------------|
| **meta** | Версия набора правил |
| **access** | Кто в каком чате с каким уровнем доступа |
| **commands** | Какая команда бота какому уровню доступна |
| **schedules** | Расписание: wallet, hourly, download, rate, raccoon_* |
| **job_params** | Тонкие настройки (интервал hourly, таймауты журнала WE…) |
| **exclude_time** | Окна времени, когда партнёра не учитывать |
| **thresholds_partner**, **wallet_limits**, **partner_groups** | Пороги и списки партнёров (wallet, Raccoon, hourly) |
| **hourly_payins**, **hourly_payouts**, … | Как собирать почасовой отчёт |
| **payout_info_rules**, **payout_ignore_phrases** | Правила для payout-анализа |
| **telegram_routes** (если есть) | Куда слать отчёты — альтернатива настройкам на сервере |
| **ui_layout** | Оформление отчётов |

Обязательные для «не сломать старт»: **meta, exclude_time, access, commands**.

## Ошибки, которые ломают систему

- Файл не Excel / обрезан при загрузке.  
- Нет обязательного листа.  
- В schedules включена задача с пустым расписанием.  
- Доступ: удалили всех админов — некому выполнить `/reload_rules`.

## Проверка без риска для prod

Команда `/rules_validate` (нужен доступ) — бот пришлёт список замечаний по структуре.

# Ошибки и диагностика

## INC-2026-06-05 — WalletEditor перестал обрабатывать файлы

| | |
|---|---|
| **ID** | INC-2026-06-05 |
| **Симптом** | WalletEditor не обрабатывает Excel; в Telegram: `❌ Ошибка: can't start new thread` |
| **Статус** | **Закрыт** (исправлено в production) |
| **Commits** | `affc689` (cleanup + observability), `5e31560` (Railway startCommand + tini) |

**Что видели операторы.** Файл уходил в очередь, затем приходила ошибка про невозможность создать новый поток. Другие процессы с Playwright (скачивание wallet/hourly/Raccoon) тоже могли деградировать.

**Причина (простыми словами).** Сервер запускался так, что главным процессом был сразу Python, без «уборщика» завершённых дочерних процессов браузера. Chromium при каждой задаче порождает много дочерних процессов; после завершения они оставались «зомби» и постепенно забивали лимит процессов/потоков в контейнере.

**Цифры расследования.**

| Показатель | До исправления (~56 мин) | После исправления (~2 ч) |
|------------|--------------------------|---------------------------|
| PID 1 | `python scheduler.py` | `tini` |
| Потоки/процессы (`ps -eLf`) | 959 | 61 |
| Zombie `chrome-headless` | 52 | 0 |

**Что сделали.**

1. **tini** стал PID 1 — reaper для zombie-детей Chromium.
2. Исправлена команда старта Railway: `[deploy].startCommand` (секция `[services.main].start` Railway не применял).
3. Усилено закрытие Playwright (page/context/browser) при любых ошибках.
4. Добавлены периодические логи здоровья процессов (`[ProcessResource/health]`).

Бизнес-логика WalletEditor, форматы Excel, маршруты Telegram и действия в Antares **не менялись**.

## WalletEditor: ошибка «can't start new thread»

| | |
|---|---|
| **Симптом** | `❌ Ошибка: can't start new thread` после отправки Excel |
| **Причины** | Накопление zombie-процессов Chromium; исчерпание лимита потоков/процессов в контейнере |
| **Проверить** | Раздел «Как диагностировать» ниже; логи `[ProcessResource/health] status=CRITICAL` |
| **Логи** | `RuntimeError: can't start new thread` в `worker_loop`; рост `zombie_chrome_count` |

Если инцидент повторится после деплоя с tini — эскалируйте техадмину: проверить, что PID 1 действительно `tini`, а не `python`.

## Как диагностировать (zombie Chrome / исчерпание ресурсов)

Команды в Railway Shell:

```bash
ps -p 1 -o pid,ppid,stat,comm,args
ps aux | grep '[c]hrome-headless' | grep defunct | wc -l
ps -eLf | wc -l
```

**Критерии здоровья.**

| Показатель | Норма |
|------------|-------|
| PID 1 | `tini` (дочерний: `python scheduler.py`) |
| Zombie chrome | 0–5 |
| Потоки/процессы (`ps -eLf`) | &lt; 200 |

**Признаки деградации.**

- Zombie chrome **&gt; 20**
- Потоки/процессы **&gt; 800**
- `RuntimeError: can't start new thread` в WalletEditor или других Playwright-задачах
- В логах: `[ProcessResource/health] status=CRITICAL`

**Функциональная проверка после деплоя:** отправить `.xlsx` в WalletEditor; убедиться, что zombie count не растёт сотнями за 1–2 часа.

# Railway — простым языком

## Где работает система

На **Railway** (облако), сервис с именем **file-analyzer**. Контейнер стартует через **tini** (PID 1), внутри — `python scheduler.py`: слушает Telegram и крутит планировщик. tini нужен, чтобы «убирать» завершённые процессы браузера Chromium (см. INC-2026-06-05).

## Что хранится «надолго» (Volume)

Папка **`/data/state`** на диске сервера (если администратор подключил Volume):

- блокировки «задача уже выполняется»;
- журнал событий по дням;
- служебные файлы WalletEditor (какие run_id уже внесены в журнал);
- диагностика отпечатков conversion (если включена).

**Неизвестно:** подключён ли Volume в вашем prod — уточните у техадмина.

## Что временное (пропадает при перезапуске)

- Сессии входа в Antares / Raccoon / Bakai (придётся залогиниться снова).  
- Скачанные Excel в `/tmp`.  
- Последний курс Bakai в `/tmp`.  
- Кэш rules на диске (восстановится из Dropbox).

## Перезапуск

При деплое или падении Railway поднимает процесс заново. Старт **не продолжится**, если нет токена бота или битый rules при первой загрузке. Задачи, которые выполнялись в момент падения, могут оставить «зависшую» блокировку — система умеет снимать старые блокировки через несколько минут (**до 10 минут по умолчанию**).

# Глоссарий

| Термин | Простое объяснение |
|--------|-------------------|
| **WalletEditor** | Робот, который по Excel меняет карты в Antares |
| **Conversion** | Робот, который анализирует файлы конверсии и ищет проблемные карты |
| **Rule** | Строка или настройка в rules.xlsx (порог, доступ, расписание) |
| **Snapshot** | «Снимок» rules в памяти сервера после чтения файла — быстрый доступ |
| **Queue** | Очередь задач WalletEditor: файлы ждут своей очереди внутри профиля |
| **Worker** | Фоновый «работник», обрабатывающий очередь одного профиля WE |
| **Registry** | Общий журнал результатов WalletEditor на Dropbox |
| **Scheduler** | Внутренний планировщик: запускает процессы по времени из rules |
| **Route** | Правило «какой тип сообщения в какой чат» (из rules или с сервера) |
| **Fingerprint** | «Отпечаток» файлов — запоминание, менялись ли данные с прошлого раза |
| **Dedup** | Пропуск повторной отправки, если данные не менялись — для conversion **ещё не включён**; для hourly/wallet — используется |
| **Observation** | Служебная запись для анализа отпечатков conversion (обычно выключена) |
| **Job** | Один запуск процесса (wallet, download, rate…) |
| **Playwright** | Программа, которая открывает сайты как браузер на сервере |
| **Dropbox** | Облачное хранилище файлов для rules и данных |
| **Railway** | Облако, где круглосуточно работает программа |
| **Antares** | Сайт antares.plus — карты, выгрузки |
| **Raccoon** | Сайт raccoon.it.com — PayIn |
| **Bakai** | Сайт bakai.kg — курс валют |
| **Профиль (WE)** | Набор логина/пароля Antares для одного оператора |
| **Планировщик** | То же, что Scheduler |

3. Включён ли режим «чаты из rules» (`TELEGRAM_ROUTES_FROM_RULES_V2`).  
4. Подключён ли Volume `/data/state` на Railway.  
5. Работает ли staging-среда (отдельной среды нет в подтверждениях).  
6. Полный перечень колонок **выходного** отчёта Conversion для бизнес-пользователя.  
7. Поведение при долгой недоступности Dropbox (оставить старые rules или нет).  
8. Точная политика restart на стороне Railway.  
9. Все бизнес-пороги Raccoon hourly (часть зашита в код: минимум операций для алерта и т.д. — без отдельной бизнес-спецификации).  
10. Список статусов Antares, допустимых в `set_status` (есть в коде ALLOWED_STATUSES — для владельца не выгружено в отдельную таблицу).

## Где информации недостаточно для описания бизнес-логики

| Область | Чего не хватает |
|---------|----------------|
| Conversion | Текстовое описание смысла каждой колонки итогового отчёта для менеджера |
| Raccoon hourly | Полные правила «просадки конверсии» в человеческих KPI |
| Payout | Какие фразы ошибок критичны — есть в rules, но нет owner-friendly каталога |
| Hourly / wallet | Как читать итоговый текст отчёта построчно |
| Исключения по времени exclude_time | Примеры из реального бизнеса |
| Уровни доступа commands | Матрица «кто что может» вне rules — нужен экспорт листа access |

Для этих пробелов имеет смысл дополнить книгу **бизнес-приложениями** (скриншоты отчётов, 1–2 страницы на процесс) — это отдельная работа от технического PROJECT_BOOK.
