# 📌 Проект — краткое руководство

## Зачем этот проект

Проект автоматизирует:
- загрузку данных (Antares, Bakai),
- анализ (conversion / payout / wallet / hourly),
- принятие операционных решений,
- доставку результатов в Telegram.

Главная ценность — **быстрое и корректное принятие решений на основе правил**.

---

## Архитектурная модель (коротко)

Проект разделён на слои:

```
Control Plane        — правила, доступы, контракты
Execution Plane      — загрузка и анализ
Observability Plane  — логи, события
Transport            — Telegram, Dropbox, Playwright
```

Каждый файл принадлежит **ровно одному слою**.

---

## Канонические термины

- **Job** — один логический запуск (download → analyze → output)
- **Analyzer** — чистая логика анализа
- **Downloader** — получение данных
- **Rules Engine** — источник истины для правил
- **Artifact** — входной или выходной файл
- **Snapshot** — зафиксированная версия правил/конфигов
- **Intent** — Telegram-команда (намерение, не выполнение)

---

## Точка входа

### `scheduler.py`

- запускает Telegram-бота  
- регистрирует команды  
- **не** планировщик  
- **не** job-движок  

Всегда остаётся тонким entrypoint’ом.

---

## Эталон архитектуры

### `analyzers/hourly_report.py`

Правильная структура анализатора:
1. подготовка данных  
2. агрегация  
3. форматирование  
4. оркестрация  

Все новые анализаторы ориентировать на этот файл.

---

## Зоны риска

### 🔴 Высокий риск

- `analyzers/conversion.py`
- `integrations/downloader.py`
- `analyzers/wallet_analyzer.py`

Правило:
> если работает — **не рефакторить без плана и тестового запуска**

---

## Правила изменений

### 1. Не смешивать роли

Если файл одновременно:
- скачивает,
- считает,
- пишет Excel,
- шлёт Telegram,

то это **технический долг**, даже если сейчас он оправдан.

---

### 2. Приоритет источников истины

```
rules.xlsx > *.yaml > дефолты в коде
```

---

### 3. Telegram — не бизнес-логика

Telegram — это:
- доставка,
- уведомления,
- UI.

Анализ не должен зависеть от Telegram.

---

### 4. Конфиг ≠ код

Любое изменение в YAML:
- меняет поведение,
- требует осознанности,
- желательно логируется.

---

## Как безопасно что-то менять

1. Определи слой (Control / Execution / Transport)
2. Проверь, не в зоне ли риска файл
3. Сравни с эталоном `hourly_report.py`
4. Меняй **одно поведение за раз**
5. Проверь Telegram-результат

---

## Если потерялся

Задай себе вопросы:
- я сейчас в Control Plane или Execution?
- это расчёт или доставка?
- где источник истины?
- можно ли сделать это без побочных эффектов?

Если ответов нет — **остановись**.

---

## Направление эволюции

1. Ввести job-контекст (`job_id`, `snapshot`)
2. Унифицировать Rules Engine
3. Отделять анализ от output
4. Медленно резать монолиты
5. Не ломать работающий код

---

## Главное правило проекта

> **Работающий код важнее красивого.**  
> Красивый код важен только если он не ломает работающий.

# Файл: **scheduler.py**





Точка входа Telegram-бота, отвечающая за ручное управление системой через команды, без автоматических job’ов и бизнес-логики.



Входы



ENV:

TG\_BOT\_TOKEN — токен Telegram-бота (обязателен)



Код:

get\_handlers() из integrations.tg\_commands — список зарегистрированных команд



Выходы / Side effects

Запуск Telegram polling (run\_polling)

Приём и обработка входящих Telegram-команд

Лог старта бота

Зависимости

telegram.ext.Application — Telegram Bot API (polling)

integrations.tg\_commands — слой intent/command routing

utils.loggers, log\_profiles — инфраструктура логирования

Контракт / инварианты



❗ Этот scheduler не запускает job’ы автоматически



❗ Вся логика — через handlers



❗ Отсутствие TG\_BOT\_TOKEN → немедленный fail-fast



Scheduler не хранит состояние, не кеширует данные, не управляет расписанием



Риски / замечания



⚠️ Название scheduler.py вводит в заблуждение

→ по факту это Telegram Bot Runner, а не планировщик



⚠️ Нет явной привязки к job-модели (job\_id / snapshot / audit)

→ важно, чтобы handlers это делали корректно



⚠️ close\_loop=False

→ допустимо, но требует дисциплины в async-коде handlers



Тест-хуки / как проверять



Локально:



export TG\_BOT\_TOKEN=...

python scheduler.py





Проверить:



бот поднимается



команды регистрируются



неизвестные команды не падают



Мокать:



get\_handlers() (вернуть 1 тестовый handler)



Telegram API (через test token)



Статус в архитектуре



Execution Plane



Manual control only



Входная точка для Control Plane через Telegram







# **Файл: main.py**

1️⃣ Текущее назначение (as-is)



Роль:

Центральный диспетчер обработки входных файлов из Dropbox.



Что делает:



принимает имя файла (и опционально вспомогательный файл)



определяет анализатор через get\_analyzer



скачивает файлы из Dropbox во временную директорию



управляет связкой основной файл ↔ card/cd



запускает анализатор



перемещает файлы в /processed



❗ Не планировщик, не анализатор, не владелец бизнес-логики.



2️⃣ Входы

ENV



DROPBOX\_INPUT\_PATH



DROPBOX\_PROCESSED\_PATH



Аргументы



filename: str — основной файл



aux\_filename: Optional\[str] — вспомогательный файл (card / cd)



Внешние зависимости



Dropbox (download / move)



Telegram (уведомления)



analyzers.selector.get\_analyzer



run\_once\_guard



3️⃣ Выходы / Side effects



файлы скачиваются в /tmp



файлы перемещаются в /processed



сообщения в Telegram



запуск анализа (побочные эффекты анализаторов)



изменение глобального состояния last\_card\_path



4️⃣ Контракты и инварианты (фактические)



❗ Один файл обрабатывается атомарно



❗ Если requires\_card=True и нет card/cd → анализ не запускается



❗ card и cd не анализируются, а только сохраняются как справочник



❗ Последний загруженный card/cd хранится в памяти процесса



❗ Анализатор сам отвечает за корректность входных данных



5️⃣ Критичные замечания / проблемы (as-is)

1\. ⚠️ Глобальное состояние last\_card\_path



живёт только в памяти процесса



ломается при рестарте



не воспроизводимо постфактум

→ противоречит Contract of Reproducibility



2\. ⚠️ Смешение ответственности

роутит файлы



управляет fallback-логикой



занимается Dropbox side effects



формирует имена артефактов



Это делает файл хрупким при расширении.



3\. ⚠️ Неявная логика определения аргументов анализатора

завязка на имя модуля



не является контрактом



легко ломается при рефакторинге



4\. ⚠️ Нет явной job-модели



нет job\_id



нет snapshot версий конфигов



Telegram уведомления не связаны с job’ом



6️⃣ Планируемые изменения (to-be, не реализованы)



(это именно список намерений, не обязательство сразу менять код)

# **Файл: run\_once\_guard.py**



**1️⃣ Текущее назначение (as-is)**



**Роль:**

**Простейший межпроцессный mutex на базе lock-файла, предотвращающий параллельный запуск одного и того же пайплайна.**



**Используется для:**



**защиты от одновременного запуска downloader’ов**



**защиты от повторного анализа одного и того же набора данных**



**2️⃣ Входы**

**Параметры**



**timeout: int = 600 — время жизни lock-файла (сек)**



**Файловая система**



**LOCK\_FILE = /tmp/dropbox\_pipeline.lock**



**3️⃣ Выходы / Side effects**



**создание файла /tmp/dropbox\_pipeline.lock**



**удаление lock-файла**



**логирование захвата / пропуска / очистки**



**4️⃣ Контракты и инварианты (фактические)**



**❗ Один процесс → один lock**



**❗ Lock считается валидным, пока:**



**файл существует**



**его mtime моложе timeout**



**❗ Устаревший lock молча удаляется**



**❗ При любой ошибке → fail-open (False)**



**5️⃣ Критичные замечания / проблемы (as-is)**

**1. ⚠️ Один lock на всё**

**LOCK\_FILE = "/tmp/dropbox\_pipeline.lock"**





**downloader**



**wallet**



**hourly**



**ручные запуски**



**👉 все они делят один mutex, даже если логически независимы.**



**2. ⚠️ Нет идентификации владельца lock’а**



**PID записывается, но не используется**



**нельзя понять:**



**кто держит lock**



**какой job его создал**



**жив ли процесс**



**3. ⚠️ Timeout = эвристика**



**если job реально идёт дольше timeout → возможен параллельный запуск**



**если job упал, но файл остался → блок до истечения таймаута**



**4. ⚠️ Не вписывается в job-модель**



**С точки зрения контракта:**



**нет job\_id**



**нет событий job\_started / job\_finished**



**mutex не связан с типом job’а**



**6️⃣ Планируемые изменения (to-be, не реализованы)**

**🔧 Минимальные (эволюционные)**



**параметризовать lock по имени job’а**

**(/tmp/{job\_name}.lock)**



**писать в lock:**



**job\_name**



**job\_id**



**started\_at**



**логировать причину снятия устаревшего lock’а**



**🧩 Архитектурные (если пойдём в job-модель)**



**заменить file-lock на job-registry**



**запретить “fail-open” при ошибках**



**связать mutex с событиями (job\_rejected, job\_running)**



**7️⃣ Тест-хуки (как проверять сейчас)**



**Локально:**



**assert acquire\_lock()**

**assert not acquire\_lock()**

**release\_lock()**





**Проверить:**



**повторный запуск в пределах timeout**



**запуск после истечения timeout**



**Эмулировать:**



**падение процесса без release\_lock**



**8️⃣ Статус в архитектуре**



**Execution Plane**



**Временный инфраструктурный костыль**



**Не часть Control Plane**



**Не обеспечивает воспроизводимость**
